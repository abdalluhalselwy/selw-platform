# ADR-0005: Supabase API Exposure, Status Transport, and Membership Policy Function

- **الحالة:** Open؛ خيارات للقرار في المرحلة 2، لا حسم.
- **التاريخ:** 2026-11-20
- **السياق:** تصميم المرحلة 1 يحتاج حداً واضحاً بين جداول PostgreSQL وSupabase Data API، ويحتاج اختيار نقل تحديثات الحالة، وقد تسبب سياسات العضوية recursion عند الاستعلام المتبادل. لا يوجد حالياً مشروع Supabase أو schema أو وثائق تحقق مرفقة.

## A. كشف قاعدة البيانات عبر Supabase Data API

**الخيار 1 — private schema وسحب صلاحيات الأدوار العامة:** وضع جداول التطبيق في schema غير مكشوف للعميل، وسحب `USAGE` وامتيازات الجداول/الدوال من `anon` و`authenticated`، وجعل الوصول عبر FastAPI DB role محدود. يلزم التحقق من قائمة schemas المكشوفة وإعدادات Data API والأدوار الفعلية.

- **الإيجابيات:** تقليل سطح الوصول المباشر، وتوافق أوضح مع قاعدة أن الكتابة تمر عبر FastAPI.
- **السلبيات:** تعقيد إضافي للتكاملات التي تعتمد Data API/Realtime، ويجب تهيئة النشر والامتيازات بعناية.

**الخيار 2 — إبقاء الجداول مكشوفة والاعتماد على RLS وحده:** منح الأدوار اللازمة الوصول للـ API مع RLS صارمة على جميع الجداول/العمليات.

- **الإيجابيات:** مسار Supabase client أبسط لبعض القدرات التي قد تحتاجها الواجهة.
- **السلبيات:** سطح تعرض أوسع؛ خطأ RLS أو grant قد يكشف بيانات. يجب إثبات تغطية جميع العمليات والأدوار وعدم وجود bypass.

**المطلوب قبل القرار:** مراجعة Supabase docs الحالية لإعداد exposed schemas وgrants/Data API وRealtime، واختبار مصفوفة الأدوار في مشروع تجريبي. كل هذه التفاصيل `NOT VERIFIED`.

## B. تحديثات حالة المهام: FastAPI SSE أم Supabase Realtime

**الخيار 1 — SSE من FastAPI:** API يرسل حالة المهمة بعد authorization وtenant checks.
- الإيجابيات: الكتابة والقراءة تمر عبر Backend؛ صلاحية وتصفية المؤسسة مركزية.
- السلبيات: اتصالات طويلة واتساع مسؤولية API والتشغيل/التوسع، واعتبارات إعادة الاتصال.

**الخيار 2 — Supabase Realtime:** اشتراك على تغييرات الحالة مع سياسات وصول DB/RLS.
- الإيجابيات: تحديثات قريبة من مصدر البيانات وتخفيف إدارة stream في API.
- السلبيات: اعتماد أكبر على grants/RLS/Realtime policy وإعدادات الخدمة؛ لا بد من إثبات العزل وعدم كشف payload حساس.

**القرار:** غير محسوم. لا تستخدم القناتين معاً قبل تعريف مصدر الحالة والتفويض والتعامل مع إعادة الاتصال. دعم كل خيار وحدوده التشغيلية `NOT VERIFIED` حتى مراجعة الوثائق الرسمية وتجربة متعددة المؤسسات.

## C. استثناء واحد محتمل لـ SECURITY DEFINER لفحص العضوية

قد يؤدي استعلام سياسة RLS عن `memberships` إلى recursion عند قراءة المؤسسة/العضوية نفسها. تعرض الخيارات التالية دون حسم:

1. **RLS غير recursive عبر فصل جداول/دوال السياسة أو claims موثقة:** يقلل امتياز الدالة الخاصة، لكن claims قد تتقادم وتحتاج invalidation آمن.
2. **دالة واحدة محدودة `SECURITY DEFINER` لفحص العضوية:** استثناء موثق ومراجع لتجنب recursion؛ يجب أن تعيد فقط boolean/أقل بيانات، وتثبت `search_path` ثابتاً، وتستخدم أسماء مؤهلة، بلا dynamic SQL، وتسحب execute من `PUBLIC` وتمنحه للدور المطلوب فقط، مع مالك غير superuser بأقل امتياز وعدم كشفها كواجهة عامة. يلزم اختبار SQL injection/privilege escalation والـ RLS semantics.

**القرار:** لا اعتماد للدالة ولا توقيعها أو صلاحياتها في هذه المرحلة. لا تُنشأ إلا بعد مراجعة رسمية وتصميم سياسة وموافقة المستخدم. يلزم إثبات أن الدالة لا توفر bypass لقراءة جداول tenant.

## حالة التحقق والمراجع

- `NOT VERIFIED`: واجهات/إعدادات Supabase Data API، schema exposure وgrants، Realtime/RLS، الأدوار والـ connection role، ودلالات `SECURITY DEFINER` في إعداد المشروع المستهدف؛ لم تجر مراجعة وثائق رسمية حديثة أو اختبار.
- المراجع الداخلية: `AGENTS.md` §§4.4, 5.2, 5.3, 11, 16.
- **العواقب:** ثلاثة قرارات أمنية/تشغيلية مطلوبة في المرحلة 2 قبل إنشاء migrations أو فتح الوصول للعميل.
